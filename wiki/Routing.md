# Маршрутизация

## Две независимые задачи

При подключении менеджер решает:

1. **Маршрут** — какой цепочкой серверов идти
2. **Адрес** — по какому ip:port стучаться в каждый сервер цепочки

## Память маршрутов

Для каждого сервера хранится три вида памяти:

| Поле | Что хранит | Когда обновляется |
|------|-----------|-------------------|
| `PreferredRoute` | Последняя успешная цепочка + JH + задержка | При успешном подключении/проверке |
| `PreferredProxyId` | Лучшая точка входа для этой цели | При успешном подключении |
| `EndpointPreferences` | Рабочий ip:port для каждого контекста | При успешном подключении к адресу |

Контексты для `EndpointPreferences`:
- `JH → сервер` (для каждой точки входа отдельно)
- `сервер A → сервер B` (для каждой пары отдельно)

Все данные сохраняются в `Data\config.json` и переживают перезапуск.

## Ранжирование маршрутов

Кандидаты делятся на классы:

| Класс | Описание |
|-------|----------|
| 0 | Подтверждённый прямой доступ (1 хоп) |
| 1 | Проверенные обходные маршруты (вход подтверждён, связи с отметкой успеха) |
| 2 | Всё остальное (непроверенные) |

Внутри класса сортировка:

1. Сложность точки входа (без OTP/скрипта проще)
2. Суммарная задержка связей
3. Число переходов
4. Подсказка proxy из исходной KiTTY-сессии
5. Точка входа, которой эти связи уже успешно ходили
6. Свежесть последнего успеха
7. Предпочтительная точка входа
8. Имя точки входа

## Порядок проверки

1. Последний успешный кандидат
2. Проверенные сохранённые связи
3. Остальные прямые JH и непроверенные пути

Если работающих точек входа нет — запускается самая простая (без OTP и access-скрипта).

## Выбор адреса для хопа

Для каждого сервера в цепочке:

1. Запомненный адрес для текущего контекста
2. Основной адрес
3. Резервные адреса (в порядке списка)

Перед SSH делается быстрый TCP-зонд, чтобы не гонять SSH по мёртвому адресу.

## Кэши неудач

| Кэш | Срок | Область |
|-----|------|---------|
| Пара «JH → сервер» | 90 сек | Только прямые попытки |
| Конкретный endpoint | 30 сек | Для каждого контекста отдельно |

Многохоповые неудачи не кэшируются (причина может быть в промежуточном сервере).

## Фоновые проверки

Запускаются только по событию (не по таймеру):

- **После успешного прохода через соседний сервер** — дешёвая проверка прямого пути
- **После успешного открытия консоли** (через 2–3 сек):
  - Допроверка лучших маршрутов
  - Допроверка прямого доступа

Для одной целевой сессии разрешена только одна фоновая проверка одновременно.

## Ограничение «Маршрут через»

Поле `RequiredPreviousServerId` запрещает прямой маршрут через JH к цели, если:
- Один private IP существует в нескольких изолированных сетях
- TCP/SSH-проверка через чужую JH формально успешна

Другой промежуточный сервер допустим только после успешной проверки связи от него к цели.

## Флаг «Сначала подключаться напрямую»

`TryDirectWithoutJumphost` добавляет перед очередью прямой SSH-кандидат. При отказе — обычные маршруты. После успеха обходного маршрута прямой перепроверяется в фоне.
