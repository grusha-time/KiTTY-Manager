# Автотесты и проверки

Раздел для разработчиков и проверяющих сборку. Основной набор находится в `src/KiTTYManager.SelfTest` и запускается из исходников; SelfTest не входит в пользовательский ZIP.

Обычный прогон — автономный: он проверяет договорённости кода и локальные сценарии без подключения к реальной инфраструктуре. Точный список проверок всегда берите из текущего кода или `--list`, а не из зафиксированного количества в документации.

## Что проверяется

Группы ниже описывают назначение тестов, а не жёсткое соответствие файлам:

| Область | Примеры проверяемого поведения |
|---|---|
| Конфигурация и перенос данных | значения по умолчанию, валидация, миграции схемы, импорт/экспорт, переносимые пути и ссылки |
| Маршрутизация и SSH | выбор маршрута и endpoint, кеши неудач, SOCKS/bridge, host key, порядок и ограничения способов подключения |
| Jumphost и KiTTY | запуск и готовность JH, TOTP/login script, временные и routed-сессии, импорт/запись параметров KiTTY |
| Firefox и веб-интерфейсы | подготовка профиля, контейнеры, локальный bridge, proxy/relay и связанные политики |
| Массовые задачи и Ansible | схема задач, выбор серверов, файлы/архивы, failure modes, workspace и протокол взаимодействия |
| Туннели и вспомогательная логика UI | Local/Remote/Dynamic tunnels, состояние сервиса, поиск справки, значения полей и чистые UI-policy |
| Обновление и регрессии | разбор релизов, безопасное применение/откат и отдельные регрессионные сценарии прошлых исправлений |

Некоторые проверки объединяют несколько областей. Имена и фактический состав текущего набора показывает `--list`.

## Запуск автономных тестов

Из корня репозитория:

```sh
dotnet run --project src/KiTTYManager.SelfTest
# Только список без выполнения:
dotnet run --project src/KiTTYManager.SelfTest -- --list
# Подстрока имени метода или названия; несколько фильтров через запятую:
dotnet run --project src/KiTTYManager.SelfTest -- --filter FailureCache,AnsibleTaskDeletion
```

Если системного `dotnet` нет, для SelfTest можно использовать `.dotnet/dotnet`. Команда `scripts/project-source.sh check` выполняет Release-сборку и полный SelfTest.

`--filter` ищет подстроку в имени метода и отображаемом названии теста. Отсутствующее значение после `--filter` завершается кодом 2; если ни один тест не найден — кодом 1. Обычный SelfTest печатает PASS/FAIL и итог в консоль, отдельный отчёт автоматически не создаётся.

## Диагностика и live-режим

Дополнительные режимы запускаются отдельно от обычной автономной проверки и требуют подходящих данных или стенда:

```sh
dotnet run --project src/KiTTYManager.SelfTest -- --diagnostics --root <path> [--output <dir>]
dotnet run --project src/KiTTYManager.SelfTest -- --live --root <path> [--output <dir>] --source <name> --target <name>
```

Перед дополнительным режимом всё равно выполняется автономный набор. Диагностический и live-режимы сохраняют свои отчёты в `--output`; без него используется `TestResults` внутри указанного `--root`.

Оба режима работают с конфигурацией из `--root`, поэтому для проверки используйте копию рабочего каталога или конфигурации. `--diagnostics` может добавить стандартные тестовые SOCKS endpoints в найденный конфиг, сохранить его и выполнить TCP/SOCKS5-пробы включённых endpoints. `--live` дополнительно может обращаться к реальным SOCKS/SSH-маршрутам. Эти режимы не являются безопасной заменой обычного offline-прогона на произвольной рабочей конфигурации.

## Мутационные проверки

Для выбранных защитных контрактов есть небольшой набор мутаций:

```sh
python3 scripts/test-audit/mutate.py
python3 scripts/test-audit/mutate.py --only <id1,id2>
python3 scripts/test-audit/mutate.py --output <path/to/results.json>
```

Список мутаций хранится в [`scripts/test-audit/mutations.json`](https://github.com/grusha-time/KiTTY-Manager/blob/master/scripts/test-audit/mutations.json). Скрипт работает в отдельной временной копии `src` и `examples`, поэтому рабочие исходники не мутирует. Для него нужен системный `dotnet` в `PATH`.

По умолчанию результаты пишутся в `TestResults/test-audit/mutations.json`; рядом создаются baseline-лог и логи отдельных мутаций.

- `killed` — выбранный тест обнаружил собравшуюся мутацию.
- `survived` — выбранные проверки пропустили изменение.
- `invalid`, `timeout` и `inconclusive` не считаются обнаруженной поломкой.

Этот набор проверяет только перечисленные контракты и не является процентом покрытия всей программы.

## Границы

Успешный SelfTest не доказывает работу WPF-интерфейса, самого Firefox, реальной SSH-инфраструктуры, серверного sudo, WHPX/QEMU или конкретной сторонней Ansible-коллекции. Loopback и policy-тесты также не заменяют проверку настоящей сети и Windows-окружения.

Для релизной проверки используйте автономные тесты как один из уровней, а Windows GUI, реальные подключения и нужные внешние компоненты проверяйте отдельно.

## Добавление тестов

Новый тест должен фиксировать конкретный контракт или регрессию и жить рядом с существующими проверками соответствующей области. Не добавляйте в документацию постоянное число тестов или снимок результатов конкретного запуска: актуальный состав показывает `--list`, а история изменений остаётся в Git.
