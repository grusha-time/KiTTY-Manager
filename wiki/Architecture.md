# Как устроен проект

Этот раздел — для понимания границ компонентов и работы с исходниками. Для настройки без кода начните с [установки](../install-instruction.md) и [навигации](Home.md).

## Что участвует в подключении

```text
KiTTY Manager (Windows)
  ├─ настройки, выбор сессий, маршруты и журнал
  ├─ KiTTY → SSH-консоль
  ├─ WinSCP → SFTP через временный порт маршрута
  ├─ Firefox → временный профиль и веб-туннель
  └─ QEMU/Linux → ansible-playbook → выбранные SSH-маршруты
```

Менеджер хранит конфигурацию и обслуживает созданные им цепочки. KiTTY, Firefox и WinSCP — отдельные процессы. Некоторые самостоятельные терминалы живут без менеджера; обслуживаемый им многошаговый маршрут зависит от его процесса.

## Каталоги исходников

| Каталог | Ответственность |
|---|---|
| `src/KiTTYManager.App` | WPF-окна, пользовательские действия, запуск внешних приложений, справка |
| `src/KiTTYManager.Core` | Конфигурация, маршруты, SSH/SFTP, импорт, задачи, профили, протокол Ansible; без зависимости от WPF |
| `src/KiTTYManager.SelfTest` | Автономные проверки и отдельно включаемая диагностика/интеграционные режимы |
| `packaging` | Подготовка runtime, проверка компонентов и Windows ZIP |
| `examples/batch-tasks` | Учебные задачи с материалами и инструкцией |
| `wiki` | Пользовательские и технические руководства |

## Основные потоки

**SSH:** RoutePlanner предлагает кандидатов, SshConnectionService проверяет адреса/авторизацию и строит маршрут. RoutePreferencePolicy, ServerEndpointPolicy и кеши учитывают уже известные успехи/неудачи. Выбор интерфейса не равен успешной сетевой проверке.

**Файлы конфигурации:** ConfigStore сохраняет модель и защищает секретные поля. ConfigTransfer/ImportWizardEngine сопоставляют переносимые данные, ImportWizardTransaction обеспечивает backup/откат применения. Portable KiTTY синхронизируется отдельно через importer/writer.

**Конструктор:** BatchTaskWindow собирает описание, BatchTaskRunner выполняет шаги через SSH/SFTP и общую интерактивную консоль. Часть проверок тестирует чистые политики, но реальный lifecycle соединения требует сетевого стенда.

**Ansible:** AnsibleTaskWorkspacePolicy готовит материалы; AnsibleVmSession запускает VM и обменивается с Python guest-agent командами, файлами и событиями через serial/named pipe. SSH из VM идёт по TCP через пробросы на хосте. Это разные каналы. Временный qcow2 overlay использует неизменяемый базовый RAW/ext4 образ.

**Firefox:** из выбранного готового источника создаётся отдельная временная копия. Управляемый SOCKS/резолвер обеспечивает доступ к панели. Обратного слияния данных профиля нет; WebSessionCleanupPolicy разделяет ответственность запуска и очистки.

**Справка:** HelpContent содержит карточки и поиск без WPF-зависимостей; HelpDialog отображает их по разделам. Поэтому семантика глобального поиска проверяется SelfTest, а реальные клавиши/размеры окна — на Windows.

## Состояние и секреты

Постоянные данные находятся рядом с приложением в `Data`; исходные portable-сессии — в `KiTTY`. DPAPI защищает значения секретов, а не весь каталог. Для работы могут создаваться временные helper-файлы; WinSCP получает некоторые секреты в аргументах процесса. Известные секреты маскируются в журналах, но произвольный пользовательский вывод требует проверки.

## Границы тестов

Unit/policy-тест не доказывает работу WPF, самого Firefox, серверного sudo или WHPX. Локальный SSH/loopback-прогон тоже не равен проверке реальной инфраструктуры. [Сборка](Building.md) и [аудит автотестов](Test-Audit.md) описывают, что именно проверяется и как воспроизвести результаты.
