# Массовые задачи: конструктор и Ansible

Кнопка **«Массовые задачи»** в главном окне открывает два режима:

- **Конструктор** — последовательность действий, собираемая в интерфейсе. Подходит для команд, файлов, проверок и диалогов с консольными программами.
- **Ansible** — настоящий `ansible-playbook` из встроенного Linux runtime. Подходит для обычных playbooks, ролей, коллекций, Jinja, handlers и декларативной настройки.

## Учебные задачи

Файлы лежат в [`examples/batch-tasks/`](../examples/batch-tasks/). Примеры доступны в репозитории и не входят в релизный ZIP. Заранее скачайте исходники репозитория либо весь каталог примеров. Копируйте папку Ansible целиком: ей нужны соседние материалы.

| Режим | Что открыть | Что понадобится |
|---|---|---|
| Конструктор | [`task-safe-smoke.kmtask`](../examples/batch-tasks/task-safe-smoke.kmtask) | Linux, SSH/SFTP, `sh`, обычные Unix-утилиты, Python 3, `tar`, `gzip` |
| Ansible | [`ansible/ansible-safe-smoke.yml`](../examples/batch-tasks/ansible/ansible-safe-smoke.yml) | Linux с Python 3 и `tar`, настроенные SSH-сессии, готовый встроенный Ansible runtime |

Обычный запуск не требует root, Интернета, внешнего HTTP-сервера или Vault-пароля. Задачи не устанавливают пакеты и не меняют службы. Начните с одного тестового сервера, затем выберите несколько **разных** серверов. Не выбирайте две сессии одного физического сервера для конструктора: у него один фиксированный рабочий путь.

Это интеграционные примеры с проверками результатов, а не полная регрессия менеджера. Выключенные дополнительные проверки не считаются пройденными.

## Конструктор: запустить пример

1. Выберите режим **«Конструктор» → «Открыть задачу из файла»**, укажите `.kmtask`.
2. На странице **«1. Серверы»** отметьте тестовые сессии. Оставьте **«Без повышения прав»**, рабочую папку `/tmp`.
3. На странице **«2. Действия и файлы»** просмотрите шаги. Все материалы уже внутри пакета; отдельно скачивать файлы не нужно.
4. На странице **«3. Туннели»** для первого запуска ничего не добавляйте.
5. На странице **«4. Проверка и запуск»** оставьте **«Продолжить на остальных»** и запустите задачу.
6. Для каждого сервера найдите `CONSTRUCTOR_ARTIFACTS_OK`, затем `CONSTRUCTOR_SMOKE_OK`. Итог сервера должен быть успешным.
7. Проверьте `Data/Downloads/<сессия и адрес>/constructor-example/`: `result.txt` со строкой `constructor=PASS`, два результата диалога, `server.txt`, скачанное дерево `tree/` и архив `tree.tar.gz`. Распакуйте архив и сравните `nested/with space.txt` с прямой копией.

**Ожидаемое предупреждение:** действие с названием «ОЖИДАЕМАЯ ОШИБКА» возвращает код 7. На нём включено «Не критично»; следующий шаг обязан показать `CONTINUED_OK`. Предупреждение демонстрирует продолжение после ошибки. Не включайте этот флаг на обычных проверках результата.

**Рабочая папка:** `/tmp/kitty-manager-constructor-example`. Первый шаг создаёт её эксклюзивно: существующий каталог, файл или ссылка останавливают проверку до загрузки материалов. После успешного запуска папка удаляется, затем проверяется её отсутствие. При критической ошибке или остановке последние шаги могут не выполниться. Посмотрите журнал и `.owner`, убедитесь, что это остаток вашего теста, и удалите только этот каталог перед повтором. Не превращайте первый шаг в безусловный `rm -rf`.

При повторе одинаковые выгрузки пропускаются. Если содержимое локального файла изменилось, передача без backup завершится ошибкой: перенесите предыдущие результаты или включите backup у нужного скачивания. Архив в примере скачивается с backup.

### Выбор действий и чтение журнала

Клик по строке отмечает действие, Shift отмечает диапазон, перетаскивание меняет порядок. **Снятие отметки не выключает шаг при запуске:** отметки используются для операций со списком, например удаления. Чтобы не выполнять действие, удалите его из копии задачи или настройте условие.

На странице запуска **«Вид журнала»** объединяет уровень и оформление. Для конструктора доступны все уровни, Info, предупреждения+ошибки или только ошибки; отдельно можно скрыть время, оставить только консоль и убрать префиксы. У Ansible — все сообщения или ошибки/предупреждения, скрытие времени и консольный вывод. Если не виден итог, отключите фильтры. Эти переключатели меняют отображение, а не исполнение шагов.

### Как собрать собственную задачу

1. Нажмите **«Создать новую задачу»**, задайте понятное имя и выберите серверы.
2. Укажите рабочую папку и режим прав. По умолчанию действие использует папку задачи; у отдельного действия можно задать свою.
3. Добавляйте действия сверху вниз. Один шаг запускается на всех подходящих серверах; следующий начинается после завершения текущего на них. Одновременно строится до пяти подключений; это не лимит в пять выполняемых действий.
4. Для каждого действия задайте название и при необходимости список конкретных серверов, условие, паузу или права.
5. Добавьте туннели, если они нужны. Выберите реакцию на ошибку сервера.
6. Сохраните шаблон для себя или экспортируйте `.kmtask`. Для передачи другим людям выбирайте включение исходных файлов в пакет; экспорт только описания не переносит материалы. Если файловых действий нет, лишний вопрос о материалах не задаётся. Если источники отсутствуют, появится их список с выбором «Сохранить без файлов» или отмены — автоматической подстановки других файлов нет.

| Действие | Практическое применение |
|---|---|
| Выполнить команду | Команда с выводом. Для строгой проверки кода возврата используйте следующий тип: обычная команда допускает некоторые ненулевые результаты |
| Проверить условие командой | Ненулевой код — ошибка; можно дополнительно потребовать текст в stdout |
| Загрузить файлы или папки | Выберите локальные материалы и путь назначения на сервере. Каталог переносится рекурсивно |
| Создать каталог | Создаёт каталог и недостающих родителей |
| Заменить текст | Буквальная замена строки в файле; это не регулярное выражение |
| Применить шаблон | Текстовый файл с `{{server.name}}`, `{{server.host}}`, `{{server.port}}`, `{{server.username}}`; это не Jinja |
| Дождаться текста и выполнить команду | Запускает команду в общей консоли, ждёт текст и отправляет действие в ту же консоль |
| Отправить текст программе | Отправляет строку в уже открытую общую SSH-консоль без ожидания приглашения |
| Диалог: ждать текст → ответить | Может запустить программу; строки ожидаемого текста и ответов образуют последовательные пары |
| Скачать с сервера | Поддерживает несколько путей, маски, каталоги, подпапку выгрузки и архивирование |
| Удалить на сервере | Удаляет путь или маску рекурсивно; указывайте только конкретные тестовые пути |

В текущем редакторе кнопка добавления источников выбирает файлы. Каталоги поддерживает исполнитель и импортированные задачи: в примере источник `files/tree` уже задан в `task.yaml`. Для своего каталога измените `Source` в исходнике задачи и импортируйте его; отдельной кнопки выбора каталога сейчас нет.

Отдельные команды не разделяют переменные оболочки и сделанный ранее `cd`. Используйте поле рабочей папки, полный путь или одну составную команду. Интерактивные действия используют одну общую консоль. «Отправить текст» отправляет текст буквально: общий режим повышения прав к нему не применяется.

Удалённые относительные пути в Upload, Template, ReplaceText, Download и Delete разрешаются от рабочей папки действия (или задачи). Локальные исходные файлы Upload/Template по-прежнему относятся к материалам задачи. Пробелы и символы оболочки в имени передаются буквально. Для удаления и архивного скачивания поддерживаются маски `*`, `?` и простые ASCII-диапазоны `[a-z]`, `[0-9]`, `[!ab]`; произвольные shell-выражения в поле пути не выполняются. Delete без совпадений ничего не удаляет; архивное скачивание без совпадений завершается ошибкой.

Для команд через `su` с паролем используется SSH PTY без скрытого лимита 60 секунд; остановить выполнение можно кнопкой отмены. Таймаут ожидания текста относится к интерактивным шагам. Если PTY уже получил команду, ошибка/таймаут не запускает её автоматически повторно через другой способ исполнения.

Условие действия (`ConditionCommand`) определяет запуск по коду возврата. Одинаковое условие вычисляется один раз на сервер за запуск и кешируется: не используйте его повторно для ожидания изменяющегося состояния. Для ожидания результата подойдёт отдельная проверка с ограниченным циклом.

`Backup` также управляет заменой при файловых конфликтах: одинаковый файл может быть пропущен; отличающийся без разрешённой замены вызывает ошибку; с backup сохраняется предыдущая версия. Параметра `OverwriteExisting` в формате задачи нет.

Получение текста/отправка ответа само по себе не доказывает правильность работы программы. Проверяйте её результат отдельным `Check`, как в примере. Тайм-аут ожидания маркера завершения может дать предупреждение о фоновой программе; это тоже не подтверждение её успеха.

Для проверки повышения прав добавьте **перед очисткой** отдельный `Check`: команда `id -u`, ожидаемый текст `0`, включённое повышение прав. Запускайте под обычной SSH-учёткой с настроенным в сессии `sudo`/`su`. Поля «Выполнить под учётной записью» поддерживаются для Command, Check, MakeDirectory, Delete, WaitForText и InteractiveWaitAndSend. Для Upload, Download, Template, ReplaceText и InteractiveSend такое сочетание отклоняется до запуска; используйте отдельную команду или Ansible. Не включайте повышенные права на всю учебную задачу: обычный SFTP продолжает использовать SSH-учётку.

Исходник пакета — [`constructor/task.yaml`](../examples/batch-tasks/constructor/task.yaml) и соседняя папка `files/`. Несмотря на расширение `.yaml`, конструктор читает **JSON**, являющийся подмножеством YAML 1.2. Произвольный YAML для этого режима не подходит. `.kmtask` — ZIP с `task.yaml` в корне. После правки исходника пересоздайте пакет через экспорт интерфейса либо ZIP содержимого `constructor/`, без внешней папки `constructor`.

## Ansible: запустить пример

1. Сохраните **всю папку `ansible/`**, включая `files/`, `templates/`, `roles/` и `collections/`.
2. Откройте **«Массовые задачи» → «Ansible» → «Проверить готовность Ansible»**. Runtime и виртуализация должны быть готовы.
3. Выберите `ansible-safe-smoke.yml`. Vault-пароль пока оставьте пустым; выберите папку выгрузок на ПК.
4. Выберите тестовые серверы в интерфейсе. Для первого запуска оставьте список туннелей пустым и обычную подробность журнала.
5. Запустите. Найдите успешный `ANSIBLE_SMOKE_OK`; в итоговой статистике не должно быть `failed` и `unreachable`.
6. В папке выгрузок откройте `<сессия и адрес>/kitty-manager-ansible-example-<суффикс>/`: `summary.json`, `results.tar.gz`, `smoke.log`. В отчёте должны быть `result: PASS` и флаги дополнительных проверок. `false` означает **не проверялось**.

Один `rescued` ожидаем: проверяется перехват намеренного `exit 7`. Запись ошибки этого шага в журнале нормальна, если выполнен `rescue`, итог успешный и присутствует финальная проверка очистки.

Пример проверяет `copy` и его идемпотентность, `replace` с backup, `template`, роль и роль локальной коллекции, `loop`, `when`, `register`, `set_fact`, `assert`, `block/rescue/always`, handler, `shell`, `command`, окружение, рабочую папку, `async` с ожиданием, `script`, `slurp`, `fetch` и `delegate_to`. Python-пример интерактивности проверяет stdin/stdout программы на сервере, а не SSH-диалоги конструктора.

Сервер и контроллер получают уникальные временные каталоги. `always` удаляет их при обычной ошибке playbook; после успеха отсутствие проверяется. При обрыве связи, принудительной остановке процесса или выключении VM выполнение `always` не гарантировано. Пути видны в журнале.

### Как указывать серверы в YAML

Обычно достаточно:

```yaml
- name: Моя задача
  hosts: all
  gather_facts: false
  tasks:
    - name: Проверить сервер
      ansible.builtin.command: hostname
      changed_when: false
```

**`all` означает серверы, выбранные в интерфейсе для этого запуска.** Менеджер сам создаёт inventory и SSH-маршруты. IP-адреса, SSH-порты и пароли в playbook для этих сессий указывать не нужно.

`inventory_hostname` — техническое имя, созданное из имени сессии: нижний регистр, неподходящие символы заменены `_`, при коллизии добавляется идентификатор. Это может отличаться и от имени сессии, и от её IP. Группы формируются из полного пути группы/подгруппы; исходная вложенная структура дерева не воспроизводится буквально.

Для выбора подмножества проще изменить выбор в интерфейсе. Если нужны разные plays по группам, сначала посмотрите технические имена в сгенерированном `<папка задачи>/.kitty-manager/inventory.yml` **во время запуска**, затем используйте стандартный `hosts: имя_группы`. Служебный inventory очищается после выполнения. Пример также выводит `inventory_hostname`, `group_names`, все выбранные имена и отображаемую группу в журнал.

Для условного действия по отображаемой группе можно использовать:

```yaml
when: kitty_group_display == 'Lab / Linux'
```

Строку берите из журнала своего запуска, а не из этого условного примера. Такой `when` пропускает действие на других серверах, но не меняет состав inventory.

### Чем отличается от обычного запуска Ansible

Язык и механизмы — обычный **ansible-core 2.16.x**. Отличается среда запуска и способ передачи параметров:

| Область | Поведение KiTTY Manager |
|---|---|
| Контроллер | Временная Linux VM; `localhost` и `delegate_to: localhost` означают VM, не Windows |
| SSH и inventory | Генерируются из выбранных сессий; `ansible_host` ведёт к пробросу на ПК, а не напрямую к исходному адресу сервера |
| Учётные данные | Из сессий; поддерживаются пароль, ключи и подготовка PPK через `puttygen`. Параметры повышения прав также берутся из сессии |
| Материалы | Копируются соседние `.yml`/`.yaml` и каталоги `roles`, `collections`, `templates`, `files`, `group_vars`, `host_vars`. Произвольный корневой `.py`, `ansible.cfg` или другая папка автоматически не переносятся; скрипты кладите в `files/` |
| Зависимости | Galaxy автоматически не скачивается. Роли/коллекции и их зависимости должны быть подготовлены заранее; системные библиотеки и Python-пакеты VM ограничены составом runtime |
| Параметры запуска | Менеджер задаёт `-i`, `--forks 5`, подробность 0–4 и при необходимости `--vault-password-file`. Поля для произвольных CLI-флагов, например `--limit`, `--tags` или `--check`, нет |
| Журнал | Используется callback менеджера; вид вывода отличается от стандартного терминала |
| Файлы Windows | Передаются явно через `kitty_manager_windows_files`; абсолютный Windows-путь не является путём внутри VM |
| Выгрузки | Пишите через `fetch` в `kitty_download_dir`; после playbook менеджер переносит подготовленные файлы из VM на ПК |
| Время жизни | Изменения контроллера не сохраняются как постоянная настроенная Linux-машина; нужные результаты выгружайте |

Предварительный поиск зависимостей в менеджере анализирует текст YAML, а не запускает полный Ansible-парсер. Он может ошибочно принять буквальный IP с двоеточием за имя коллекции. Поэтому URL туннеля в примере собирается из `bind_host` и `bind_port` через Jinja. Если обычный playbook отклонён с неожиданным именем коллекции, проверьте это место отдельно.

Не переопределяйте генерируемые `ansible_host`, `ansible_port` и `ansible_ssh_executable`, если хотите использовать маршруты менеджера. Playbooks для более нового Ansible или сторонних коллекций требуют проверки совместимости с поставляемым runtime.

Стандартные механизмы описаны в [документации ansible-core 2.16](https://docs.ansible.com/projects/ansible-core/2.16/index.html), включая [соседние роли](https://docs.ansible.com/projects/ansible-core/2.16/playbook_guide/playbooks_reuse_roles.html). Пример поставляет небольшую локальную коллекцию без внешних зависимостей; её успех не подтверждает совместимость всех Galaxy-коллекций.

### Переменные менеджера

| Переменная | Назначение |
|---|---|
| `kitty_server_display` | Исходное отображаемое имя сессии |
| `kitty_group_display` | Отображаемый путь группы |
| `kitty_upload_dir` | Папка явно переданных Windows-файлов внутри VM |
| `kitty_download_dir` | Папка выгрузки данного сервера внутри VM; используйте её в `fetch.dest` |
| `kitty_manager_tunnels` | Список туннелей данного сервера: `name`, `kind`, `bind_host`, `bind_port`, `destination_host`, `destination_port` |

Внешний playbook получает рабочую копию в `Data/Templates/`. После выполнения интерфейс предлагает сохранить или удалить созданную папку. Для повторного использования можно хранить готовую папку задачи там; служебные файлы менеджер очищает отдельно.

### Дополнительные проверки Ansible

Флаги находятся в `vars` в начале playbook. Включайте их по одному после успешного обычного запуска. Редактируйте тот файл, который выбран в интерфейсе; если используется сохранённая рабочая копия, изменение исходного файла на диске не обновит её автоматически.

**Windows → VM → сервер:** подготовьте один обычный текстовый файл, поставьте `smoke_test_windows_upload: true` и добавьте рядом в `vars`:

```yaml
kitty_manager_windows_files:
  - '%USERPROFILE%\Downloads\kitty-example.txt'
```

Файл должен существовать до запуска. Список читает менеджер до выполнения Ansible: используйте именно простой список строк с абсолютными Windows-путями и `%ПЕРЕМЕННЫМИ%`, не Jinja. Выключение флага не отменяет чтение списка — удалите его, если файл больше не нужен. Пример требует ровно один переданный файл и сверяет размер/checksum на сервере.

**Повышение прав:** `smoke_test_become: true`. Выберите обычную SSH-учётку с настроенными `sudo`/`su` и root-паролем, если требуется. Пример сначала требует UID не 0, затем проверяет UID 0 через `become`. Вход сразу под root намеренно не засчитывается как проверка повышения.

**Vault:** `smoke_test_vault: true`; в поле Vault-пароля введите **`kitty-example-only`**. `files/demo-vault.yml` содержит только публичную учебную переменную. Она расшифровывается и проверяется с `no_log: true`. Это демонстрационный пароль, не секрет для использования в своих задачах. Проверка `no_log` не является исчерпывающим тестом маскирования всех секретов менеджера.

**Remote-туннель:** `smoke_test_remote_tunnel: true` и настройка ниже.

## Проверка туннелей в обоих режимах

### Remote: запрос с сервера к HTTP-сервису на ПК

На Windows с установленным Python 3 откройте PowerShell и запустите отдельный учебный HTTP-сервис:

```powershell
$exampleHttpDir = Join-Path $env:TEMP ([guid]::NewGuid().ToString())
New-Item -ItemType Directory -Path $exampleHttpDir | Out-Null
[IO.File]::WriteAllText((Join-Path $exampleHttpDir 'tunnel.txt'), "kitty-tunnel-ok`n", [Text.UTF8Encoding]::new($false))
py -3 -m http.server 18080 --bind 127.0.0.1 --directory $exampleHttpDir
```

В интерфейсе задачи добавьте туннель:

| Поле | Значение |
|---|---|
| Имя | `Example HTTP` |
| Тип | Remote |
| Адрес / порт прослушивания на сервере | `127.0.0.1:18081` |
| Назначение со стороны ПК | `127.0.0.1:18080` |
| Серверы | Все выбранные разные серверы |

Для Ansible достаточно включить флаг. Для конструктора добавьте перед действием «Опционально: HTTP…» обычную команду:

```sh
touch /tmp/kitty-manager-constructor-example/enable-remote
```

Результат конструктора — `REMOTE_OK`; Ansible проверяет точное содержимое HTTP-ответа и указывает `remote_tunnel: true` в отчёте. Если сервис или туннель недоступен, включённая проверка обязана завершиться ошибкой. После проверки остановите HTTP-сервис `Ctrl+C` и удалите созданную вами временную папку.

### Local: ручной запрос с ПК к серверу

Local-порт принадлежит ПК: **один Local-туннель должен быть назначен ровно одному выбранному серверу**. Временный HTTP-сервис на тестовом сервере можно подготовить в отдельной SSH-консоли:

```sh
example_http_dir=$(mktemp -d /tmp/kitty-local-http.XXXXXX)
printf 'kitty-local-ok\n' > "$example_http_dir/tunnel.txt"
python3 -m http.server 18082 --bind 127.0.0.1 --directory "$example_http_dir"
```

Добавьте Local `127.0.0.1:18083 → 127.0.0.1:18082`, назначьте нужную сессию. Пока задача работает, на ПК выполните:

```powershell
(Invoke-WebRequest -UseBasicParsing http://127.0.0.1:18083/tunnel.txt).Content
```

Ожидается `kitty-local-ok`. Для конструктора можно включить «Держать туннели открытыми после завершения всех шагов», проверить запрос и нажать «Остановить». У Ansible такого удержания после playbook нет: для ручной проверки добавьте до окончания playbook `ansible.builtin.pause` с `seconds: 60`. Затем убедитесь, что порт закрылся. Остановите тестовый HTTP-сервис и удалите его отдельную временную папку.

## Какие проверки требуют отдельного запуска

| Сценарий | Что наблюдать |
|---|---|
| Несколько разных серверов | Результат и файлы каждого сервера; нет подмены/смешения выгрузок |
| Выбор серверов отдельного шага | Шаг выполняется только на назначенных сессиях; остальные явно пропущены |
| Пароль / OpenSSH / PPK / ключ с passphrase | Каждый выбранный способ отдельно проходит задачу |
| Обрыв и восстановление связи на тестовом стенде | Журнал потери/возврата связи, запросы о повторе неоднозначных действий, итоговые файлы без неожиданных повторов |
| Критическая ошибка | В копии конструктора отключите «Не критично» у ожидаемого `exit 7`, сравните оба режима реакции на ошибку |
| Остановка | Задача прекращается, туннели закрываются; проверьте остатки рабочих файлов |
| Подробность / секреты | Сравните обычный и подробный журнал на учебных значениях; реальные секреты в примеры не добавляйте |

Успех обычного примера подтверждает только выполненные проверки. Windows GUI, запуск/остановка VM, все маршруты, поведение при отключении питания и все варианты сторонних Ansible-модулей требуют своего стенда.
