# Firefox Containers TEST

Локальная экспериментальная ветка: `codex/firefox-containers`.
ZIP содержит программу и runtime; MD и SHA256-файл в комплект не добавляются.
Точка возврата: `firefox-before-containers-20260910` (исходный master).
Работоспособность Windows/реальных KiTTY-туннелей проверяется отдельно от локальных тестов.

## Запуск

1. Распаковать TEST ZIP в отдельную папку. Стабильный менеджер и его Data сохранить.
2. Импортировать конфигурацию менеджера обычным способом. Указать установленный Firefox (128+).
3. Перед первым открытием закрыть основной Firefox: его профиль копируется один раз.
4. Открыть веб-интерфейс. Рабочий профиль находится в `Data/FirefoxContainersTest/profile`.
   Стартовая служебная вкладка автоматически закрывается после открытия первого интерфейса.
5. Открыть другой интерфейс: используется тот же Firefox, отдельный контейнер и отдельный туннель.
   Повторное открытие той же записи создаёт вкладку в её контейнере через действующий туннель.

Контейнер привязан к ID сессии + ID веб-интерфейса. Переименование/перенос между группами
не удаляет данные. Разные записи, включая одинаковый URL, имеют независимые cookies.
Сохранённые пароли и исключения сертификатов общие в профиле. Разные сертификаты на одном
имени/порту могут снова требовать подтверждения; контейнеры этого ограничения не устраняют.
Никакого обратного мержа в личный профиль и удаления рабочего профиля нет.
Смена исходного профиля в настройках не пересоздаёт уже накопленный рабочий профиль.
Контейнеры не удаляются автоматически: это намеренное сохранение cookies и данных сайтов.

## Дополнительная вкладка в том же туннеле

Обычная новая вкладка через «+» может открыться вне контейнера и не получить маршрут.
Чтобы открыть дополнительный адрес через уже работающий туннель, нажать правой кнопкой
по вкладке интерфейса → «Дублировать вкладку», затем в дубликате ввести нужный HTTPS URL
с портом. Контейнер сохраняется. После подтверждения сертификатного исключения
перезагрузить первоначальную страницу приложения. Автоматическое наследование контейнера
для обычной кнопки «+» в этой версии не добавлено.

## Как устроена тестовая загрузка

Новое расширение пока не подписано Mozilla. На каждом запуске Firefox менеджер через
локальный Marionette загружает его как временное расширение (постоянный ID).
Это временная установка расширения, а не временный профиль: контейнеры и пользовательские
данные остаются на диске. Подпись Firefox не отключается, папка установки Firefox и
глобальные политики не меняются. Для продуктового выпуска нужна отдельная проработка
подписанной установки; механизм Marionette предназначен для TEST.
Marionette доступен локальным процессам на случайном порту, пока открыт этот Firefox.
Не использовать эту сборку как замену стабильной версии до приёмки.

Расширение общается с менеджером через loopback HTTP с секретом на один запуск.
Страницы не получают этот секрет. Прямые HTTP(S)/WebSocket-запросы без активного маршрута
блокируются; глобальный прокси профиля также направлен на отказное соединение.
WebRTC включён, включая профили, созданные предыдущей TEST-сборкой с отключённым WebRTC.
Голосовой UDP-трафик использует сетевой маршрут ОС, а не контейнерный SOCKS-туннель.
Звонки требуют сетевой доступности медиасервера; работа через конкретную сеть/VPN
и конфликты одинаковых медиадресов проверяются отдельно. Блокировка HTTP(S) при
отключении менеджера не является блокировкой WebRTC-медиа.
Firefox Sync отключён в копии: она не должна
синхронизировать изменения с личным профилем/аккаунтом.
DNS: расширение передаёт имя в локальный SOCKS relay; relay сначала применяет таблицу
соответствий выбранной сессии, затем использует DNS системы менеджера. Host/SNI сохраняются.

## Закрытие и сбои

После закрытия последней вкладки контейнера его локальный relay закрывается.
Настройка закрытия KiTTY после Firefox теперь применяется к последней вкладке контейнера.
Если флажок выключен, консоль остаётся, как раньше. При полном выходе менеджера активные
контейнерные подключения отключаются. Firefox может остаться открытым и сохранять данные,
но страницы не должны продолжать сетевую работу без менеджера.
Перед новым запуском механизма закрыть оставшийся Firefox TEST: захват живого профиля
и восстановление маршрутов в чужой экземпляр не выполняются.
После сбоя ничего не мержится и профиль не удаляется. Не удалять профиль для устранения
ошибки запуска: сначала сохранить его полную резервную копию при закрытом Firefox.

## Приёмка в Windows (ещё не подтверждена локальной сборкой)

- Первый импорт с закрытым Firefox; отказ с занятым источником без его изменения.
- Повторный запуск при открытом личном Firefox: источник уже не нужен.
- Два разных интерфейса, два KiTTY-туннеля, нужный DNS/IP в каждом.
- Одинаковые домен и порт в разных сетях: ответы и cookies не пересекаются.
- HTTP, HTTPS, WebSocket, редиректы, всплывающие окна и загрузки реальных панелей.
- Сохранение/обновление настоящего пароля, автозаполнение после закрытия и нового запуска.
- Сохраняемое сертификатное исключение после перезапуска, включая конфликт сертификатов.
- Закрытие одной вкладки не закрывает туннель остальных вкладок того же контейнера.
- Обрыв KiTTY, выход/аварийное завершение менеджера, отсутствие прямого обхода туннеля.
- Перезапуск Firefox, обновление Firefox, сохранность контейнеров и их cookies.
- Замер времени повторного открытия и роста размера после работы на реальных панелях.

## Локальные проверки

```
.dotnet/dotnet run --project src/KiTTYManager.SelfTest -c Release -- --filter "Firefox containers"
.dotnet/dotnet run --project src/KiTTYManager.SelfTest -c Release -- --firefox-container-smoke /path/to/firefox /absolute/test-directory
```

Вторая команда создаёт искусственный профиль и два тестовых SOCKS-сервера с одинаковым
доменом. Она запускает настоящий headless Firefox и проверяет маршрутизацию и cookies;
не обращается к реальным сетям и не использует личный профиль. Артефакты сохраняются
в указанной тестовой папке. Это не проверка GUI Windows, настоящих паролей или TLS-рисков.

## Проверено на сервере 2026-09-10

- 353 автономных теста: успешно, ошибок 0.
- Настоящий Firefox 155.0.1 / Linux headless: один домен, два разных SOCKS-сервера,
  раздельные cookies, блокировка отключённого маршрута.
- Второй запуск Firefox: cookies и привязки контейнеров сохранились; источник повторно
  не читался. Временное расширение успешно загружено повторно.
- Активные страницы пытались обращаться к локальному контрольному серверу: прямых
  подключений не было, включая период после отключения bridge менеджера.
- После открытия двух интерфейсов в настоящем Firefox остаются ровно две вкладки:
  служебная стартовая вкладка удалена.
- Регрессионная проверка переводит `media.peerconnection.enabled` из false в true
  в обоих файлах уже существующего профиля (prefs.js и user.js).
- `node --check` расширения и `git diff --check`: успешно.

Это не подтверждает Windows GUI, настоящие KiTTY-туннели, сохранение/автозаполнение
паролей и сертификатные диалоги. Их список приёмки приведён выше.

## Откат

Сначала сохранить изменения тестовой ветки коммитом. Затем `git switch master`.
Чистая сборка стабильной ветки выпускает прежний ZIP. Git не возвращает runtime Data.
Для пользовательского отката закрыть TEST и запустить прежний менеджер из его папки.
Профиль TEST сохранить: в нём могут быть новые пароли.
